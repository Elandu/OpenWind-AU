# Engineering Validation Protocol

OpenWind-AU separates software regression testing from independent engineering validation.

## Golden-case principle

A golden case must not be generated by the same production calculation path that it is intended to
test. Expected values are to be prepared independently and then locked as review evidence.

Each case should record:

- a stable case identifier and descriptive title;
- the applicable standard edition and source references;
- the independent reviewer and review date;
- the complete calculation inputs;
- expected intermediate values for `VR`, `Mc`, `Md`, `Mz,cat`, `Ms`, and `Mt`;
- expected directional `Vsit,b`;
- expected Clause 2.3 building-orthogonal `Vdes,theta` values where applicable;
- the tolerance used for each numerical comparison; and
- notes explaining any deliberately unsupported or manually reviewed path.

The repository schema is stored at
`data/validation/golden-case.schema.json`. Reviewed case files should be added under
`data/validation/golden-cases/`.

## Minimum coverage before the v0.8 verification milestone

The reviewed suite should contain at least 30 cases and cover the implemented behavior across:

- Regions A0-A5 and B1/B2;
- reviewed representative C/D coastal cases once #13 is complete;
- multiple assessment heights;
- TC1 through TC4, including TC3.5 interpolation;
- single-category and complete ordered mixed-terrain profiles;
- shielded and unshielded cases;
- flat terrain, hills, ridges, and escarpments;
- topographic boundary/eligibility cases once #14 is complete;
- multiple building orientations;
- Clause 2.3 circular interpolation, sector boundaries, governing ties, and the applicable minimum;
- invalid and incomplete inputs that are expected to fail closed.

## Review rules

1. Do not copy licensed standards text into the repository.
2. Clause/table references and derived numeric expectations may be recorded when permitted.
3. Reviewer identity and review date must represent a real completed review.
4. If a standard amendment changes an expected value, add or revise the case and document the
   superseded basis rather than silently changing the number.
5. Production code changes that alter a reviewed golden value require explicit engineering review.
6. A tolerance must be tight enough to detect calculation changes and must not be chosen merely to
   make a failing implementation pass.

## Test layering

The validation program should retain separate layers:

- unit tests for equations, interpolation, parsing, and edge cases;
- API/MCP parity tests for transport and schema behavior;
- golden cases for independently calculated engineering expectations;
- synthetic terrain fixtures for geometric/topographic selection behavior;
- anonymised project comparisons for whole-workflow regression;
- private real-project parallel runs before wider deployment.

This structure keeps software correctness evidence distinct from professional engineering approval.
