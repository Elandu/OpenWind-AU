# v0.8 Release Plan

The v0.8 milestone is focused on turning the implemented site wind-speed workflow into an
independently verified engineering engine. It is not a pressure-design release.

## Release blockers

The following issues must be completed before the v0.8 engineering milestone can be described as
independently verified:

- #11 — verify the applicable AS/NZS 1170.2 edition and derived lookup assets.
- #12 — build an independent engineering golden-case regression suite.
- #13 — implement reviewed Region C/D distance-to-coast regional wind-speed interpolation.
- #14 — automate the Clause 4.4.2 most-adverse section and escarpment eligibility checks.
- #16 — package a versioned production data bundle with provenance and digests.

No reviewer identity, review date, lookup approval, or amended-edition compliance may be inferred or
filled automatically. These fields record real engineering review activity.

## v0.8 supporting work

The following work improves usability and operational readiness but does not substitute for the
engineering gates above:

- #15 — reviewed terrain-transition map editor and source-referenced import.
- #18 — private production deployment, observability, and provider hardening.

## Post-v0.8 productisation

Persistent organisations, users, projects, immutable assessment snapshots, and audit history are
tracked in #17. The preferred sequence is to validate the calculation service privately on real
projects before coupling it to a larger application layer.

Design-pressure work is tracked separately in #19 and remains downstream of the v0.8 verification
gate. Pressure coefficients or design actions must not be added from memory or secondary summaries.

## Release evidence

A v0.8 release candidate should include all of the following:

1. A completed amended-edition verification record for every implemented normative path.
2. Independent reviewer/date metadata for every approved derived lookup asset.
3. A machine-readable golden-case suite with independently calculated intermediate and final values.
4. Production dataset and lookup manifests with content digests and attribution.
5. Passing Python, JavaScript, package-install, report-render, REST/MCP parity, and container checks.
6. A successful `openwind-au check --json` run under the same production configuration intended
   for deployment.
7. A documented private-project comparison log showing how discrepancies were investigated and
   converted into regression cases.

Passing automated tests is necessary but does not replace engineering review.
